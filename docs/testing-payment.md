# Чек-лист: шаг оплаты (ApiPay / Kaspi Pay)

В проекте нет тестового фреймворка (`package.json` — только `vite dev/build`,
`eslint`, `prettier`, ни `vitest`/`jest`/`playwright` не установлены, файлов
`*.test.*`/`*.spec.*` нет). Ручной чек-лист вместо автотестов — если фреймворк
появится позже, эти же сценарии можно будет перенести в него почти без правок.

Проверяется шаг 4 мастера оформления сертификата (`src/routes/certificate.tsx`)
и обвязка: `src/lib/apipay.ts`, `src/routes/api/certificates/create.ts`,
`src/routes/api/certificates/status.$id.ts`, `src/routes/api/webhooks/apipay.ts`.

## Предусловия

- Применена миграция `supabase/migrations/20260821000000_add_apipay_fields.sql`
  (иначе всё падает на записи в БД ещё до вызова ApiPay — см. диагностику от
  2026-08-21, код ошибки `PGRST204`).
- Для сценариев, помеченных **[нужен sandbox-ключ]**, в переменных окружения
  должны быть заданы `APIPAY_API_KEY` (sandbox) и `APIPAY_WEBHOOK_SECRET`.
  Без них эти сценарии выполнить нельзя — не тестировать вслепую (см. Блок 1.6
  задачи от 2026-08-20 / Блок 3.2 задачи от 2026-08-21).

## Сценарии

### 1. Валидный номер + валидная сумма → счёт создаётся [нужен sandbox-ключ]
1. Дойти до шага 4 с любой суммой ≥ 20 000 ₸.
2. Выбрать «Оплатить по номеру телефона», ввести валидный тестовый номер в
   формате `8XXXXXXXXXX`.
3. Отметить согласие с условиями, нажать «Отправить запрос на оплату».
4. **Ожидается:** кнопка показывает спиннер → экран переключается в режим
   ожидания («Проверьте уведомление в приложении Kaspi Pay на номере …») →
   в Supabase (`certificates`) появляется строка с `payment_status: pending`,
   `payment_channel: phone`, `payment_provider: apipay`, заполненным
   `provider_invoice_id`.
5. Через `POST /invoices/{id}/simulate-status` (`{"status":"paid"}`) в
   песочнице ApiPay сымитировать оплату.
6. **Ожидается:** в течение ~3–6 секунд (один цикл поллинга) мастер сам
   переходит на шаг 5, показывает карточку сертификата с номером `RTS-…`.
   В БД `payment_status: paid`, `paid_at` заполнен.

### 2. Невалидный номер телефона → ошибка до отправки на сервер
1. Дойти до шага 4, выбрать «Оплатить по номеру телефона».
2. Ввести заведомо неверный номер: короче 11 цифр, начинающийся не с «8»
   (например `77001234567` — с «7», не «8»), либо оставить пустым.
3. Нажать «Отправить запрос на оплату».
4. **Ожидается:** запрос на `/api/certificates/create` **не отправляется**
   (проверить по вкладке Network/`read_network_requests` — счётчик запросов
   не растёт); под полем телефона появляется красная подсказка "Введите номер
   в формате 8XXXXXXXXXX (11 цифр)" — не только в общем списке ошибок внизу.
   Экран остаётся на выборе способа оплаты.
5. Ввести корректный номер — подсказка у поля пропадает.

_Уже проверено вручную 2026-08-20 (клиентская валидация блокирует запрос) и
доработано 2026-08-21 (подсказка теперь показывается прямо у поля, не только
внизу списком)._

### 3. Сумма 0 / отрицательная → блокируется на фронтенде
1. Открыть `/certificate?kind=amount&amount=0` (или отрицательное значение)
   напрямую по ссылке.
2. **Ожидается:** `validateSearch` в `certificate.tsx` отбрасывает
   `amount <= 0` — сумма не подставляется, шаг 1 открывается с суммой по
   умолчанию (первый вариант из `fixedAmounts`, ≥ 20 000 ₸), а не с нулём.
3. На шаге 1 попытаться уменьшить сумму меньше `MIN_AMOUNT` (20 000 ₸) через
   поле «своя сумма» и нажать «Подарить».
4. **Ожидается:** `validateStep1` блокирует переход, показывает
   `cert.errMinAmount` ("Минимальная сумма — 20 000 ₸"), запрос на сервер не
   уходит. До шага 4 с нулевой/отрицательной суммой дойти невозможно в
   принципе — оплата какого-либо `total <= 0` на сервер не отправляется.

### 4. Сервер недоступен / ApiPay вернул ошибку → общее понятное сообщение
1. Дойти до шага 4, выбрать любой способ оплаты, корректно заполнить.
2. Смоделировать сбой — один из вариантов:
   - **[без ключа, воспроизводится всегда сейчас]** без `APIPAY_API_KEY` —
     нажать «Отправить запрос»/«Показать QR».
   - **[нужен sandbox-ключ]** временно испортить `APIPAY_API_KEY` (лишний
     символ) — имитирует 401 от ApiPay.
   - Отключить интернет на клиенте перед нажатием кнопки (сетевой сбой уже
     на fetch, ответ от сервера вообще не приходит).
3. **Ожидается во всех трёх случаях:** пользователь видит один из понятных
   текстов — «Приём платежей ещё не подключён…» (нет ключа) или «Не удалось
   создать счёт на оплату. Попробуйте ещё раз.» (прочие сбои) — **никогда**
   сырой JSON/стектрейс/технический код. Кнопка становится снова активной,
   можно повторить попытку. Техническая причина при этом видна **только** в
   логах сервера (`vercel logs` / `console.error`), не в браузере — проверить
   `read_network_requests`/DevTools, что тело ответа с деталями (`error_code`,
   Postgres-ошибка и т.п.) не рендерится напрямую в DOM.

_Строка 1 (без ключа) реально воспроизведена 2026-08-21 — см. диагностику:
`POST /api/certificates/create` упал на записи в Supabase ещё до вызова
ApiPay (не про ключ вовсе, а про непринятую миграцию) — это тоже пример
"сервер вернул ошибку", и он уже сейчас показывает только текст "Не удалось
создать счёт на оплату. Попробуйте ещё раз.", без деталей PGRST204._

### 5. QR без номера телефона → счёт создаётся, показывается QR [нужен sandbox-ключ]
1. Дойти до шага 4, оставить способ «Оплатить по QR» (по умолчанию).
2. Поле телефона не должно отображаться вовсе.
3. Отметить согласие, нажать «Показать QR для оплаты».
4. **Ожидается:** запрос уходит на `/api/certificates/create` с
   `paymentChannel: "qr"`, `payPhone: null` — сервер вызывает
   `POST /invoices/qr` (без `phone_number` в теле, см. `src/lib/apipay.ts`).
   На экране появляется QR-код (`invoice.qrCode`) или, если ApiPay вернул
   только ссылку, кнопка-переход по `invoice.payUrl` — реальные данные, не
   старый demo-payload `RAITHAI-DEMO;...` (тот убран из кода полностью).
5. `simulate-status` → `paid` → переход на шаг 5, как в сценарии 1.

## Дополнительно (не входило в исходный список, но покрывает найденный баг)

### 6. Категории ошибок ApiPay не текут "как есть" на клиент
1. В `src/routes/api/certificates/create.ts` и
   `src/routes/api/webhooks/apipay.ts` найти каждое место, где `err`/
   `provider_error_code` уходит в `Response.json` клиенту.
2. **Ожидается:** клиенту всегда уходит одно из: `error` (машинный код вроде
   `apipay_not_configured`/`invoice_create_failed`, использующийся только для
   `if`-веток в коде, не показывается напрямую) или `errorCategory` — одна из
   `phone_not_registered | not_configured | rate_limited | validation |
   unknown` (`categorizeApipayErrorCode`, `src/lib/apipay.ts`). Сырых `code`
   от ApiPay (`client_not_found`, `kaspi_session_not_configured` и т.п.) в
   ответах API быть не должно — только в `console.error` и в колонке
   `provider_error_code` таблицы `certificates`.
3. Смоделировать `client_not_found` (номер, не зарегистрированный в Kaspi, в
   песочнице) **[нужен sandbox-ключ]** — вебхук должен прийти со
   `status: "error"`, `error_code: "client_not_found"`; после этого
   `GET /api/certificates/status/{id}` — вернуть
   `paymentStatus: "failed", errorCategory: "phone_not_registered"`, а мастер
   — показать "Этот номер не зарегистрирован в Kaspi Pay. Проверьте номер или
   оплатите по QR." (не общий "Не удалось создать счёт…").

## Что нельзя проверить без sandbox-ключа

Пункты, помеченные **[нужен sandbox-ключ]** выше (сценарии 1, 5, часть 4 и 6)
— требуют `APIPAY_API_KEY`/`APIPAY_WEBHOOK_SECRET` в переменных окружения.
Без них они не тестировались и тестироваться не должны (см. ограничение
задачи — не тестировать вслепую без ключа).
